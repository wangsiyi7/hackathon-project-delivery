# Adaptation Guide

This guide explains how to adapt Hackathon Project Delivery beyond the original UCWS use case.

## Universal Hackathon Pattern

Every serious hackathon submission has four surfaces:

1. **Product**: what actually runs.
2. **Evidence**: GitHub, demo URL, screenshots, tests, changelog, provenance.
3. **Narrative**: problem, user, solution, differentiation, roadmap.
4. **Submission channel**: Project Wall, Devpost, custom form, organizer portal, GitHub issue, or demo-day deck.

The skill should keep all four visible.

## Event Audit Checklist

- Event homepage
- Tracks or categories
- Team size rules
- Submission deadline and timezone
- Required fields
- Accepted demo formats
- Required repository format
- Screenshot/video/logo requirements
- Authenticated endpoints or manual form constraints
- Judging criteria
- Public examples or prior submissions

## UCWS Defaults

For UCWS-style events, assume:

- tracks may include Agents, Skills, Applications, Deep Research
- Project Wall fields need public URLs and strong summaries
- GitHub repository links matter
- community vote, AI evaluation, and expert judging may all inspect the project differently
- official APIs may require login, even when event metadata is public

## Devpost Defaults

For Devpost-style submissions, add:

- inspiration
- what it does
- how it was built
- challenges
- accomplishments
- what is next
- built-with tags
- video/demo URL

## Accelerator Or Demo Day Defaults

For investor or accelerator contexts, add:

- customer segment
- pain intensity
- market wedge
- traction or validation
- business model
- team advantage
- demo narrative


## Final Rule

Do not optimize only for "can submit." Optimize for "can be understood, trusted, and remembered."

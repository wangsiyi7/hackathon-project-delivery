# 适配指南

这份指南说明如何将 Hackathon Project Delivery 从 UCWS 扩展到未来所有黑客松和 Demo Day。

## 通用黑客松模式

任何严肃的黑客松提交都有四个表面：

1. **产品**：真正能运行的东西。
2. **证据**：GitHub、Demo URL、截图、测试、更新记录、来源说明。
3. **叙事**：问题、用户、解决方案、差异化、路线图。
4. **提交渠道**：Project Wall、Devpost、自定义表单、主办方后台、GitHub issue 或 Demo Day deck。

这个 Skill 应该始终让四个表面都可见。

## 比赛审计清单

- 比赛主页
- 赛道或分类
- 团队人数规则
- 截止时间和时区
- 必填字段
- Demo 格式
- 仓库要求
- 截图、视频、Logo 要求
- 需要登录的接口或人工表单限制
- 评审标准
- 公开样例或往届项目

## UCWS 默认假设

对于 UCWS 类型赛事，可以默认关注：

- 赛道可能包括 Agents、Skills、Applications、Deep Research
- Project Wall 字段需要公开链接和强摘要
- GitHub 仓库链接很重要
- 社区投票、AI 评审和专家评审会从不同角度查看项目
- 官方 API 可能需要登录，即使赛事元数据公开

## Devpost 默认假设

对于 Devpost 类型提交，额外准备：

- inspiration
- what it does
- how it was built
- challenges
- accomplishments
- what is next
- built-with tags
- video/demo URL

## 加速器或 Demo Day 默认假设

对于投资人或加速器语境，额外准备：

- 客户群体
- 痛点强度
- 市场切入口
- 牵引力或验证
- 商业模式
- 团队优势
- Demo 叙事

## 推荐输出文件

```text
README.md
PROJECT_SUBMISSION.md
project-payload.json
docs/FINAL_READINESS_REPORT.md
docs/DEPLOYMENT.md
docs/DEMO_SCRIPT.md
assets/screenshot.png
assets/logo.svg
```

## 最终原则

不要只优化“能提交”。要优化“能被理解、被信任、被记住”。
